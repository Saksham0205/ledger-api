# Assumptions

1. **Spec numbering.** The assignment jumps from section 5 to section 7 (there is no section 6) and
   section 4 ends with a typo ("transactions.t."). I assumed nothing is missing and implemented
   sections 1-5 and 7-11.
2. **Single currency.** No currency field. Amounts and balances are decimals with at most 2 places.
3. **Money representation.** Stored as `NUMERIC(18,2)`; sent and returned as JSON numbers. Amounts must be
   > 0, have at most 2 decimals and be at most 1,000,000,000. Numeric strings such as `"10"` are rejected.
4. **IDs.** Account and transaction IDs are server generated UUIDs. Clients can never supply `id`,
   `balance` or `created_at` (extra fields are rejected with 400).
5. **Required fields.** `description` is required (max 255 chars) because the spec lists it as a mandatory
   transaction field. `reference_id` is required (max 100 chars). Text inputs are trimmed.
6. **Duplicates.** A repeated `reference_id` on the same account returns **409 Conflict** with code
   `DUPLICATE_TRANSACTION` and the original transaction in `details.transaction`; no row is created and the
   balance is untouched. The same `reference_id` may be used on different accounts.
7. **Status codes.** Validation/malformed input 400, unknown account 404, duplicate 409, insufficient
   balance 422, unexpected 500. An invalid UUID is 400; a well-formed but unknown UUID is 404.
8. **Balance.** Debiting the exact balance is allowed (balance becomes 0). Balances can never go negative.
9. **History.** Sorted by `created_at DESC` with `id DESC` as a tie-breaker. Defaults: `page=1`, `limit=10`,
   max `limit=100`. Invalid values are rejected, never silently corrected. A page past the end returns an
   empty `data` array with correct metadata. An account with no transactions returns `total_pages: 0`.
10. **Transfers (bonus).** Implemented as `POST /api/v1/transfers`. A transfer writes two linked ledger rows
    (a debit on the source and a credit on the destination) that share a `transfer_id` and the supplied
    `reference_id`. The `reference_id` is idempotent: if it already exists on either account the request is a
    409 and nothing changes. Transferring to the same account is rejected (400).
11. **Immutability.** Transactions cannot be edited or deleted via the API or via SQL (trigger). Accounts
    also have no update/delete endpoints because none were requested. Corrections are made by posting a new
    opposite transaction, as in a real ledger.
12. **Auth and scale.** No authentication/authorisation (not requested). Single Postgres instance; the
    row-lock approach is correct for this scope, and sharding or a ledger-per-shard design is out of scope.
13. **Timestamps.** `created_at` is generated by the database in UTC (`timestamptz`) and returned in ISO 8601.
14. **Migrations.** Schema changes are applied only through migrations (`npm run migration:run`); the app
    never auto-syncs the schema.
